下面是 AI 写的「文件」页，原样加载，接口换成了这里模拟的。现在选的是「接口一直不回来」：页面打开就去拉列表，请求发出去以后什么也没回来。

第 2 份会一直停在骨架屏上。第 1、3 份等到第 15 秒，换成「没能加载文件」（第 3 份是「没能加载文件列表」）和一个「重试」按钮。把接口切回「正常」，点「重新打开页面」，等列表出来，再切回「一直不回来」去点「上传文件」：第 2 份的按钮变成「上传中」，然后就停在那里，再也点不了；第 1、3 份同样在 15 秒后报错，按钮恢复。

三份页面的状态其实写得很全。我们拦截接口造了 22 个场景，整理成下面 17 项判定，51 格里只有 4 格没走通，全在第 2 份。这篇讲这 4 格背后的两件事：每个「进行中」为什么都要有出口，元素消失时焦点该去哪；再给一段能让任何页面的接口「坏掉」的脚本，最后是规则。

范围：三个全新的 Claude Code subagent 各写一次，2026-10-31；2026-11-18 在 macOS 的 Chrome 157 里，用 Playwright 拦截接口逐个场景跑，375px 宽的手机视口。prompt 和原始数据在附录。

表里绿的部分，三份都做到了：空列表有说明，500、403、断网、返回格式不对都会报错、给「重试」，第 3 份还把四种情况分开说了；删除前的确认框点名是哪个文件；删除中再点、上传连点三下，都只发一次请求；删掉一行，焦点落在相邻一行的「删除」上。我们还试了两个删除请求同时在途、中间再上传一个文件，三份的列表都没有乱（[输出](/blog/lab/ai-states/data/concurrent.txt)）。

再看红格落在哪。三份都加载了团队的 UI 规范 skill，它要求交付前检查「空 / 加载 / 失败 / 无权限」，还写着「弹层关闭：焦点回到触发它的那个元素」。规范写了的这几样，三份都没漏；4 格红正好落在规范没写的两件事上：请求超时，和弹层以外的元素消失后焦点去哪。规范没写不等于一定做不到，第 1、3 份就自己设了超时，可三份里也就有一份没做。

## 每个「进行中」都要有一个出口

一个状态叫「加载中」「删除中」「上传中」，就必须有办法离开它：成功、失败，或者等太久。前两个出口是请求给的，第三个只能页面自己给。

原因在 fetch 上。fetch 的选项里没有超时（[MDN 的 RequestInit](https://developer.mozilla.org/en-US/docs/Web/API/RequestInit) 列出的参数里没有 timeout），请求发出去以后，只要服务端不回、连接也没断，它返回的 Promise 就既不成功也不失败。页面把「进行中」挂在 `then` 和 `catch` 上，这两个都不触发，状态就结束不了。

第 2 份就是这样。列表等了 20 秒还停在骨架屏；删除等了 30 秒，那一行一直是「删除中」；上传等了 30 秒，底部按钮一直是「上传中」，而且是禁用的。禁用本来是为了防止重复提交，没有出口以后，它就把整个上传功能锁死了，只能刷新页面。第 1、3 份给每个请求都设了 15 秒的超时，到时间就按失败处理：报错、按钮恢复，列表还给一个「重试」。

**怎么看出来。** DevTools 网络限速的预设里有「离线」，没有「一直不回来」。用第三部分的脚本把接口切到「一直不回来」，然后把页面上每个会发请求的按钮都点一遍，等 15 秒，看每个「进行中」是不是都结束了。

**怎么写对。** 给每个请求都加上超时，超时按失败处理。第 1 份的写法：

```js title="第 1 份：所有请求都走这一个函数"
const REQUEST_TIMEOUT_MS = 15000   // fetch 本身没有超时，不设就会一直等

async function request(url, init = {}) {
  const res = await fetch(url, { ...init, signal: AbortSignal.timeout(REQUEST_TIMEOUT_MS) })
  if (!res.ok) throw new HttpError(res.status)
  return res
}

// 报错时单独认出超时，给一句用户看得懂的话
if (err.name === 'TimeoutError') return '等了很久没有响应，请稍后重试。'
```

等多久合适，要看接口。可以参考 Nielsen Norman Group 的[响应时间三个界限](https://www.nngroup.com/articles/response-times-3-important-limits/)：10 秒「is about the limit for keeping the user's attention focused on the dialogue」，更长的等待，它建议给出完成百分比和一个能中断的入口。下面是我们的取舍：普通的列表、删除这类请求，本来不该要 10 秒；等到这个时间还没回来，与其让用户继续盯着转圈，不如告诉他出了问题、给一个重试的按钮。第 1、3 份取了 15 秒，比 10 秒多留了一点余量给慢网络，也是合理的值。上传大文件这类本来就慢的操作，要换成显示进度和「取消」，而不是一个固定的超时。

**还有哪里会这样。** 提交表单、支付确认、保存草稿、轮询任务状态、长连接断线重连。凡是界面上有一个「……中」的地方，都问一句：如果它一直不回来，用户最后看到什么？

## 元素消失时，焦点要有去处

用户正聚焦着的元素一旦被删掉或藏起来，焦点不会自己挪到旁边的元素上：`document.activeElement` 变成 `body`，屏幕上看不到焦点在哪。在 Chrome 里，元素被藏起来以后（删掉的情况我们没有测），下一次按 Tab 会从原来的位置往后走，所以元素后面紧跟着的是什么，用户就被带到哪里，不一定是他想去的地方。

三份页面在最明显的地方都处理了：删掉一行，焦点移到相邻一行的「删除」上；全删光，焦点移到「上传文件」或搜索框；取消确认框，焦点回到刚才点的「删除」。漏掉的是一个不那么明显的地方：「重试」。第 2 份点了「重试」以后，开始重新加载，整个错误提示连同「重试」按钮一起被藏了起来，`document.activeElement` 变成了 `body`；列表加载出来以后再按一次 Tab，焦点直接跳到底部的「上传文件」，整张刚加载出来的列表被跳过了：错误提示在页面结构里排在列表后面，从它原来的位置往后走，自然就越过了列表。第 1、3 份在重新加载之前，先把焦点挪到了列表区域上，再按一次 Tab，落在第一个文件的「删除」上（[输出](/blog/lab/ai-states/data/focus-retry.txt)）。读屏软件上会怎样，我们没有测。

**怎么看出来。** 在 DevTools 的 Console 里点「眼睛」图标，加一个实时表达式 `document.activeElement`，然后只用键盘操作：Tab 到按钮上，按回车，看实时表达式变没变成 `body`，再按一次 Tab，看焦点落到了哪里。凡是点了以后自己会消失的按钮，都要这样试一次。

**怎么写对。** 先决定焦点去哪，再让元素消失。第 1 份的写法：

```js title="第 1 份：重试前先把焦点交给列表区域"
// <section id="files" tabindex="-1">：tabindex="-1" 让它能被脚本聚焦，又不会出现在 Tab 顺序里
els.retry.addEventListener('click', () => {
  els.region.focus()   // 重试按钮马上要被藏起来，焦点先放到它所在的区域上
  loadFiles()
})
```

**还有哪里会这样。** 关掉一个提示条、删掉一个筛选标签、清空搜索框旁边的「×」、切换标签页以后旧内容被换掉、确认框关闭后触发它的那一行已经不在了。这些地方的焦点该去哪，没有统一答案，但一定要有人决定，不能交给浏览器。

## 验收：给页面接一个会坏的接口

状态要靠让接口坏掉来验，不能等它自己坏。这篇的脚本就做这件事：贴进 DevTools 的 Console 回车，右下角出现一个面板，可以让之后的每个请求「正常 / 慢 3 秒 / 一直不回来 / 返回 500 / 断网」，面板上实时显示有几个请求在等、各等了多久。贴进控制台的脚本，刷新页面就没了，所以它管不到页面第一次加载；开头的演示能管到，是因为它在页面脚本之前就把这段代码注入了进去。

<SnippetRun src="ai-states/net-snippet.js" panel="__net_lab__" label="在这篇文章上打开面板" note="这篇文章本身不发请求，在这里打开面板只能看看样子；要试，就复制脚本，到你自己的页面上运行。它只接管 fetch，不管 XMLHttpRequest 和 WebSocket；请求带了 signal 时照样能被取消，所以页面自己的超时会生效。再运行一次就关掉，fetch 恢复原样。" />

拿到一个页面，按这个顺序过一遍：

1. **「慢 3 秒」**，触发一次重新拉数据的操作（点重试、切换筛选、下拉刷新）：加载状态有没有、像不像页面本来的样子。
2. **「返回 500」「断网」**，把每个会发请求的按钮点一遍：每种失败有没有说人话、有没有重试、失败以后数据有没有被错误地改掉（比如删除失败，这一行却没了）。
3. **「一直不回来」**，再点一遍，等到超过你定的超时：每个「……中」都要结束。
4. 全程只用键盘，凡是点完会消失的按钮，看焦点去了哪、下一次 Tab 落在哪。

## 给 AI 的规则

团队规范里已经写了的空、加载、出错，三份都做到了，规则只补规范没写、这一次也有人漏了的两件事：

```md title="写进 AGENTS.md 或 skill 的状态规则"
- 每个请求都要设超时（fetch 没有默认超时），例如 `AbortSignal.timeout(15000)`；超时按失败处理：
  给出能看懂的提示和重试入口，把按钮上的「……中」和禁用状态恢复过来。
- 一个操作会让当前聚焦的元素消失或被藏起来时（重试、删除、关闭），先把焦点移到下一个合理的位置，再移除元素。
- 交付前在浏览器里自测，接口模拟脚本是 net-snippet.js（/blog/lab/ai-states/net-snippet.js，先下载到本地）。
  用 Playwright 的 `addInitScript` 只注入一段，内容依次是 `window.__netLabHeadless = true;`（不画面板）和脚本全文；
  多段 init 脚本的执行顺序没有保证，不要拆开注入。分两次测：
  首次加载：在这一段末尾再加 `window.__netLab.set('hang');`，打开页面，等过超时，确认加载状态结束了（reload 后又会是 hang）；
  按钮：不加这一句，等页面正常加载完，再用 `page.evaluate(() => window.__netLab.set('hang'))` 切过去，
  把每个会发请求的按钮点一遍，等过超时，确认每个「……中」都结束了；
  再只用键盘把会自己消失的按钮按一遍，确认焦点没有落回 body。
```

## 附录：实测材料

三份页面由三个全新的 Claude Code subagent 在 2026-10-31 各写一次，模型是当时会话的默认模型 Claude Opus 5.5（subagent 继承它，汇报里没有自己写模型名）。prompt 里只有需求，派发时另加了一句「写完后简短汇报：加载了哪些 skill、读了哪些文件、交付前怎么检查的」。它们继承这台机器上的全局配置 `~/.claude/CLAUDE.md` 和 skill 列表。据它们自己的汇报（[摘录](/blog/lab/ai-states/data/provenance.txt)）：三份都加载了团队的 UI 规范 skill（ui-conventions），它要求交付前检查「空 / 加载 / 失败 / 无权限」；都读了同目录下的 prompt.txt 和 api/files.json；第 1 份开头遇到 API 限额中断，恢复后从头写完。三份都在交付前拦截接口自测过各种状态，第 3 份说它自测时修掉了一个搜索中上传会报错的问题。

```text title="prompt（三次只有最后一行的文件名不同）"
用 HTML + CSS + 少量原生 JS 写一个单文件页面：移动端 H5 的「文件」页。

内容和行为：
- 顶部导航栏：中间标题「文件」
- 一个搜索框，占位文字「搜索文件」，输入时按文件名过滤列表
- 文件列表：打开页面时用 fetch 从 ./api/files.json 拉取，返回的格式是 [{ "id": 1, "name": "2026Q3 报告.pdf", "size": "2.4 MB", "updatedAt": "10月28日" }, …]；每行显示文件图标、文件名、大小和修改时间，右侧一个「删除」按钮
- 点「删除」先弹确认，确认后用 fetch 发 DELETE ./api/files/{id}，成功后把这一行从列表里去掉
- 底部固定一个「上传文件」按钮：点了以后用 fetch 发 POST ./api/upload（先不用真的选文件，发一个空请求就行），接口返回新文件的 { id, name, size, updatedAt }，成功后把它加到列表最上面

把完整代码写到这个文件：……/files1.html
```
