# 写博客文章

## 核心

这个博客的每一篇都要**有据可查**：写进正文的结论，来自实际跑过的命令、量过的数字、读过原文的规范，不是转述和印象。综述体、观点体的稿子不符合本站要求。

动笔前先判断文章属于哪一类，两类的写法不同：

| 类型 | 例子 | 人称 | 风格基准 |
| --- | --- | --- | --- |
| 工具 / 经验类 | 作者自己的配置、工作流、踩坑记录 | 用「我」，写作者真实的配置和经历 | `tmux-guide.mdx`、`nvim-tmux.mdx` |
| 教学类 | UI 审美系列这类讲规律、讲方法的文章，内容不是作者的亲身实践 | 视情况而定，中性叙述也可以；**不要替作者编个人经历**，比如「我平时都这么写」 | 下文「教学类的呈现」一节 |

拿不准属于哪类，或者某段经历是不是作者的，问用户，不要猜。

**系列导读**是例外：只写背景、痛点、写给谁、读完得到什么、后面每篇回答什么问题，最后一句收尾。证据引用已有的实测，不要求要点速览、可粘贴的规则附录和「至少跑 2 次」。目录每项写成这一篇要回答的问题，不列名词。基准：`ai-ui-taste.mdx`。

## 动笔前：先过竞品关

1. 列出这个主题下 2–3 篇最好的同类文章，英文、中文各找一些，选搜索靠前、被引用最多的。每篇都要实际打开读过，写下标题和链接。
2. 用一句话写清楚：这篇给出了什么它们没有的东西。可以是真实的实测数据、中文语境（中文排版、国内 App / H5 场景）、可以直接复制的规则或配置。
3. 写不出这一句，就先别写这篇，回去找角度。

这一句不写进正文，但要在交稿说明里给用户看。

## 两类共用的规矩

- `##` 是部分，`###` 是节，`####` 是小节。标题里不写序号，CSS 会自动编号。标题尽量短，目录里不要折行。
- 不写「总结」段落，不写文末的参考文献列表。链接在第一次提到时直接放进正文。
- 至少一个附录，放一份完整、能直接拿走的东西：配置、规则文件、完整代码。
- 没验证过的内容要标出来，不能混在陈述句里：工具 / 经验类用 `<Callout type="todo">`；教学类用正文里一句平实的话，例如「iOS Safari 的真机还没测，以上是 Chrome 模拟触屏的结果」。
- 规范引用要落到数字和出处链接。WebFetch 返回的是摘要，不是原文：要直接引用的原话和数字，用 `curl -sL <url> | rg '<关键词>'` 在原始页面里搜到才算核实，搜不到就标「待核实」。

## 工具 / 经验类的写法

照基准文章写。动笔前至少读完其中一篇的前 60 行和任意一个 `<Callout type="pit">`。

| 部分 | 要求 | 基准文章里的样子 |
| --- | --- | --- |
| 开头 | 1–3 段短文：讲什么、作者的处境或分工。可以有一张小表 | 「我的分工很简单：」加一张表 |
| 范围锚定 | 一句话说明以什么为准：版本、设备、日期，附件在哪 | 「本文以 nvim 0.11.5、tmux 3.6 为准……配置在文末附录」 |
| 前置说明 | 可选。读者必须先知道的约定，用 `<Callout title="先说……">` | 「先说前缀键」 |
| 正文 | 先给东西再解释：表格（按键→作用、场景→用什么→原因）、带 `title=` 的代码块、演示组件，然后用短段落讲为什么 | |
| 附录 | 完整配置 | 「附录：我的完整配置」 |

- 每个 `##` 部分至少一处第一手证据：实际跑过的命令和原样输出、测出来的数字、真实报错。
- 演示组件后面跟「几个值得注意的地方：」加列表。
- Callout：tip 写要点，pit 写真实踩过的坑（带原始报错），warn 写容易误操作的地方，todo 写没实测的，try 写练习。基准文章大约每 30–70 行一个。
- 超过约 30 分钟的长文，每个 `##` 下面第一行写导语：`**主题** · 阅读约 N 分钟 · 前置：……`，再加一句「学完这一部分，你能……」。阅读时间按 `blog/src/lib/posts.ts` 的 `readingMinutes` 估：中文每分钟约 400 字，代码块不计。

## 教学类的呈现

教学类文章讲的是「为什么」和「怎么判断」，读者要在几十秒里抓住结论，再按需往下读。写成实验报告（表格堆叠、原始输出摆在正文里）就不合格。参照的范文是 OpenAI 的 [GPT-6 系列模型指南](https://openai.com/zh-Hans-CN/index/practical-guide-building-gpt-6/)。

**结构（按顺序）**

1. **description 一句话**：页面会把它显示成标题下的副标题，控制在一行半以内。
2. **开头两段短文**：问题是什么，这篇怎么做。接着就放一张图，让读者先看到东西。
3. **要点速览**：一个加粗的「要点速览」，加 3–5 条要点；每条先写一句加粗的结论，再跟一句解释。
4. **正文各节**：每节第一句先定调（例如「漏掉的问题有一个共同点：代码里看着都对，要量才看得出来」），下面是加粗开头的要点。
5. **附录**：可以直接粘贴的规则；过程材料（prompt、脚本、原始输出、量错过的地方）全部放这里，不放正文。

**证据怎么呈现**

- 能画出来的就不要列数字：颜色和对比度画成真实颜色的色块；前后差别用「之前 / 之后」两张截图；多次产出并排放在一张图里。
- 插图用 `blog/src/components/Figure.astro`：柔和的渐变底，一行说明。说明写清楚这张图是什么、在什么条件下得到的。
- 正文里尽量不放表格；确实要比较多个维度时，最多一张，而且要短。
- 代码块只给改后的写法，原值写在注释里，一段代码只讲一件事。不用 diff 的红绿底，在这一页里太抢眼。
- Callout 少用，一篇一两个就够了；能用一句正文说清楚的，不要做成提示块。

## UI 审美系列的额外要求

1. **实测 AI 的真实产出。** 文章的证据来自实测，写清楚这几样（详细的放附录）：
   - 给 AI 的原始 prompt、模型名、日期，同一个 prompt **至少跑 2 次**。
   - 产出的完整原文放进 `blog/public/lab/<文章名>/`，正文只放必要的摘录或截图。
   - **在浏览器里量渲染结果**（坐标、尺寸、计算后的样式、对比度），不能只读代码。很多问题只有量出来才看得到。
   - 被测对象可以是一个全新的 subagent，prompt 里只写需求。subagent 会继承用户的全局配置（`~/.claude/CLAUDE.md`、skill 列表），测到的是「这台机器上的 AI」，不是空白模型，这一点要在附录里写明。
2. **实测说了算。** 测出来的结果和预想不一样时，按测出来的写，可以直说「原本以为……，量下来是……」。AI 做对的地方照实写；不要为了凑反面例子改写实测结果。
3. **修法用代码给。** 每个问题配一小段修正代码，不能只用文字描述。
4. **演示里的反面例子必须来自实测。** 实测里没出现的问题，不放进演示。
5. **附录里有一份能直接粘贴的规则**：给 AGENTS.md 或 skill 用的条目，或者 CSS token。

## 口吻

- 不用「笔者」。「我」「我们」按文章类型和上下文选，不强求。
- 大白话、短句。避免「赋能」「极致」「优雅地」这类词，也不要宏大的开场。
- 数字要具体：「等 300 毫秒」，不写「稍等片刻」。比值写成「4.5:1」，不加空格，避免折行。
- 中英文、数字之间加空格。正文段落里，数字和单位之间用 `&nbsp;`，避免折行；表格、标题、代码块里不用。

## 交稿前

- frontmatter：`title`、`description`、`date`、`tags`，新稿加 `draft: true`。
- 按读者看到的样子整页截图（桌面浅色、桌面深色、手机各一套），逐屏看：间距、折行、对齐、图片底色。
- 演示组件按 `.claude/skills/building-post-demos/SKILL.md` 做，并且在浏览器里验证过。
- **REQUIRED：** 发布前按 `.claude/skills/reviewing-blog-posts/SKILL.md` 过一遍审稿。
