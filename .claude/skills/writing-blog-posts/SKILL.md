# 写博客文章

## 核心

读者读完一篇，要能做一件以前做不到的事：看出一类问题、做对一个决定、拿走一段能用的代码或规则。**只描述「发生了什么」的文章没有收获**，不管数据多扎实。

这个博客的每一篇还要**有据可查**：正文里的结论，来自实际跑过的命令、量过的数字、读过原文的规范。

两条合起来就是：**证据用来支撑判断，判断才是正文。**

## 收获从哪来：现象 → 原理 → 用法

最常见的失败是停在第一层。写之前先把每个发现推到第三层：

| 层 | 例子（对话页布局） | 读者能拿走什么 |
| --- | --- | --- |
| 现象 | 三次里有两次，输入框比消息列宽 24&nbsp;px | 什么也拿不走。这是那三份文件的事 |
| 原理 | 两块各自算宽度，只在某个窗口宽度下碰巧相等 | 一个解释：为什么会错、换个页面还会不会错 |
| 用法 | 一条边只能有一个主人；缩放窗口看边会不会分开 | 一个判断方法和一个写法，下次自己就能用 |

每个 `###` 小节都要过两个问题：

1. **换一个页面，这一节还用得上吗？** 只对这几份实验文件成立的，是现象，挪进附录或删掉。
2. **读者不看实验数据，只看这一节的第一句，能学到东西吗？** 不能，就把第一句改成原理或判断。

## 动笔前：先写这三样

不写进正文，但要在交稿说明里给用户看。

1. **读完能做的 3 件事。** 写成「读者能……」，每件对应正文的一个部分。写不出来，说明这篇还只是现象。
2. **竞品关。** 这个主题下 2–3 篇最好的同类文章（英文、中文都找，选搜索靠前、被引用多的），实际打开读过，写下标题和链接。再用一句话说清楚：这篇给出了什么它们没有的东西，比如真实的实测数据、中文语境、可以直接粘贴的规则。写不出这一句，就别写。
3. **骨架。** 先列 `##` 和 `###` 标题，再读一遍：每个标题都是一个判断（「一条边只能有一个主人」），而不是一个话题（「对齐」）或一个事件（「AI 漏掉了什么」）。

## 文章类型

| 类型 | 例子 | 人称 | 基准 |
| --- | --- | --- | --- |
| 工具 / 经验类 | 作者自己的配置、工作流、踩坑记录 | 用「我」，写作者真实的配置和经历 | `tmux-guide.mdx`、`nvim-tmux.mdx` |
| 教学类 | UI 审美系列这类讲规律、讲判断的文章 | 中性叙述或「我们」；**不替作者编个人经历**，比如「我平时都这么写」 | 下文「教学类」一节 |

拿不准属于哪类，或者某段经历是不是作者的，问用户，不要猜。

**系列导读**按教学类写，但不要求要点速览和附录规则。它也要给读者一样马上能用的东西：一个判断框架，或者一套检查流程，不能只是目录。目录每项写成这一篇要回答的问题，不列名词。基准：`ai-ui-taste.mdx`。

## 两类共用的规矩

- `##` 是部分，`###` 是节，`####` 是小节。标题里不写序号，CSS 会自动编号。标题尽量短，目录里不要折行。
- 不写「总结」段落，不写文末参考文献。链接在第一次提到时放进正文。
- 至少一个附录，放一份完整、能直接拿走的东西：配置、规则文件、完整代码。
- 规范引用要落到数字和出处链接。WebFetch 返回的是摘要，不是原文：要直接引用的原话和数字，用 `curl -sL <url> | rg '<关键词>'` 在原始页面里搜到才算核实，搜不到就标「待核实」。
- **规范是论据，不是内容。** 引一条规范，是为了支撑本节的判断；不要为了显得全面，把几份规范怎么说排成一段。一节里通常一两处引用就够了。

## 限定语：集中说一次

没测过的、只在 Chrome 里测过的、样本只有两份的，都要说，但**只说一次，说在一个地方**：教学类放在开头范围说明里一句话，加附录里的细节；工具 / 经验类用 `<Callout type="todo">`。

正文里每段都加「这只说明……，不代表……」，读者就拿不到任何结论。**测过的部分要敢下结论**，测出来怎样就怎样写。

反例（不要这样写）：

> 这些数据支持本次序列中的状态反转和采样点连续性，不足以证明任意连点、每一帧位置连续或速度连续。

改成：

> 两份都能接住半途反向：开到一半关上，菜单从当前位置往回退，没有跳回起点。原因是它们用的是 transition，而不是每次重播的 keyframes。

## 工具 / 经验类的写法

照基准文章写。动笔前至少读完其中一篇的前 60 行和任意一个 `<Callout type="pit">`。

| 部分 | 要求 | 基准文章里的样子 |
| --- | --- | --- |
| 开头 | 1–3 段短文：讲什么、作者的处境或分工。可以有一张小表 | 「我的分工很简单：」加一张表 |
| 范围锚定 | 一句话说明以什么为准：版本、设备、日期，附件在哪 | 「本文以 nvim 0.11.5、tmux 3.6 为准……配置在文末附录」 |
| 前置说明 | 可选。读者必须先知道的约定，用 `<Callout title="先说……">` | 「先说前缀键」 |
| 正文 | 先给东西再解释：表格（按键→作用、场景→用什么→原因）、带 `title=` 的代码块、演示组件，然后用短段落讲为什么 | |
| 附录 | 完整配置 | 「附录：我的完整配置」 |

- 每个 `##` 部分至少一处第一手证据：实际跑过的命令和原样输出、测出来的数字、真实报错。
- 演示组件后面跟「几个值得注意的地方：」加列表。
- Callout：tip 写要点，pit 写真实踩过的坑（带原始报错），warn 写容易误操作的地方，todo 写没实测的，try 写练习。基准文章大约每 30–70 行一个。
- 超过约 30 分钟的长文，每个 `##` 下面第一行写导语：`**主题** · 阅读约 N 分钟 · 前置：……`，再加一句「学完这一部分，你能……」。阅读时间按 `blog/src/lib/posts.ts` 的 `readingMinutes` 估：中文每分钟约 400 字，代码块不计。

## 教学类的写法

教学类讲「为什么」和「怎么判断」。读者要在几十秒里抓住结论，再按需往下读。

**结构（按顺序）**

1. **description 一句话**：写读者能拿走什么，不写「我们做了什么实验」。页面把它显示成副标题，控制在一行半以内。
2. **开头两三段**：问题是什么；读完能做到什么；一句话的范围说明（被测对象、日期、浏览器、样本数，细节在附录）。接着放一张图，让读者先看到东西。
3. **要点速览**：加粗的「要点速览」加 3–5 条。每条先写一句加粗的**原则**，再跟一句解释它为什么成立。不要写成「三次里有两次……」的实验结果。
4. **正文**：每个 `###` 讲一条原则，按下面的节奏走，每一步通常一两段，不用小标题把它们隔开：
   - **判断**：第一句就是原则本身，例如「一条边只能有一个主人」。
   - **为什么**：它背后的机制。读者懂了机制，没见过的情况也能推出来。
   - **怎么看出来**：一个读者自己十秒能做的检查，比如「把窗口从 1440 拖到 1024，看两条边会不会分开」。
   - **怎么写对**：一段改后的代码，原值写在注释里。
   - **还有哪里会这样**：同一条原则在别的界面上怎么出现，两三个例子。这一步把现象变成原理。
   - **实测**作为证据穿插在「为什么」或「怎么看出来」里，一两句加一张图，不单独成段。
5. **最后一个正文部分**：把这几条原则合成一个读者能照着做的检查流程，或者解释它们为什么都逃过了现成工具（机制，不是工具对比表）。
6. **附录**：可以直接粘贴的规则和代码；过程材料（prompt、脚本、原始输出、量错过的地方、工具逐个对比）全部放这里，不放正文。

**不要用的骨架**

- 「它做对了什么 / 它漏掉了什么」：这是实验报告的结构，读者拿到的是这几份文件的成绩单。AI 做对的地方，写成「这一条现在的模型已经会了，不用再写进规则」，一两句带过。
- 每节都是「规范怎么说 / 实测 / 修法 / 怎么查」四段：规范和工具会挤掉原理。
- 工具对比大表放正文。

**证据怎么呈现**

- 能画出来的就不要列数字：颜色画成真实颜色的色块；前后差别用「之前 / 之后」两张截图；随时间变化的东西（动画、滚动）画成曲线。
- 插图用 `blog/src/components/Figure.astro`：柔和的渐变底，一行说明，写清楚这张图是什么、在什么条件下得到的。
- 正文里最多一张表，而且要短。
- 代码块只给改后的写法，原值写在注释里，一段代码只讲一件事。不用 diff 的红绿底。
- Callout 一篇一两个就够了；能用一句正文说清楚的，不做成提示块。

## UI 审美系列的额外要求

1. **实测 AI 的真实产出，当作证据。** 写清楚这几样（详细的放附录）：
   - 给 AI 的原始 prompt、模型名、日期，同一个 prompt **至少跑 2 次**。
   - 产出的完整原文放进 `blog/public/lab/<文章名>/`，正文只放必要的摘录或截图。
   - **在浏览器里量渲染结果**（坐标、尺寸、计算后的样式、逐帧采样、对比度），不能只读代码。
   - 被测对象可以是一个全新的 subagent，prompt 里只写需求。subagent 会继承用户的全局配置（`~/.claude/CLAUDE.md`、skill 列表），测到的是「这台机器上的 AI」，不是空白模型，这一点写进附录。
2. **实测说了算。** 测出来和预想不一样，按测出来的写，可以直说「原本以为……，量下来是……」。AI 做对的地方照实写；不要为了凑反面例子改写实测结果。
3. **实测里找不到问题，就换更难的需求再测**，不要把「都做对了」写成一篇。一篇需要的是能讲出原理的失败，或者一组能讲清「为什么这样就对」的对照。
4. **修法用代码给。** 每条原则配一小段改后的代码。
5. **演示里的反面例子必须来自实测。** 实测里没出现的问题，不放进演示。
6. **附录里有一份能直接粘贴的规则**：给 AGENTS.md 或 skill 用的条目，或者 CSS token。只收 AI 实测里真没做到的；它已经做对的不用写。

## 口吻

- 不用「笔者」。「我」「我们」按文章类型和上下文选，不强求。
- 大白话、短句、敢下结论。避免「赋能」「极致」「优雅地」这类词，也不要宏大的开场。
- 数字要具体：「等 300 毫秒」，不写「稍等片刻」。比值写成「4.5:1」，不加空格，避免折行。
- 中英文、数字之间加空格。正文段落里，数字和单位之间用 `&nbsp;`，避免折行；表格、标题、代码块里不用。

## 交稿前

- frontmatter：`title`、`description`、`date`、`tags`，新稿加 `draft: true`。
- 把每个 `###` 的第一句单独抄出来读一遍：连起来应该是一份能用的原则清单。读起来像实验记录的，回去改。
- 按读者看到的样子整页截图（桌面浅色、桌面深色、手机各一套），逐屏看：间距、折行、对齐、图片底色。
- 演示组件按 `.claude/skills/building-post-demos/SKILL.md` 做，并且在浏览器里验证过。
- **REQUIRED：** 发布前按 `.claude/skills/reviewing-blog-posts/SKILL.md` 过一遍审稿。
